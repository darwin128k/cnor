# Event host: thermostat

A complete embedding example: compile the policy on a desktop, load the
image once, and run its entry point for each sensor event. C owns the sensor
and relay state; the script implements hysteresis (on below 19 C, off above
22 C, unchanged in between). No compiler API is linked by the host.

From the repository root:

```sh
cmake -S . -B build-event -DCMAKE_BUILD_TYPE=Release -DCNOR_BUILD_EXAMPLES=ON -DCNOR_BUILD_TESTS=ON
cmake --build build-event
ctest --test-dir build-event --output-on-failure
./build-event/examples/event-host/cnor_event_host build-event/examples/event-host/thermostat.tbc
```

On Windows add `.exe`; multi-configuration generators may put executables in
`Release/`. The image is generated by `cnor compile` during the build.

To build the target without the compiler, reuse the desktop-generated image:

```sh
cmake -S . -B build-event-vm -DCMAKE_BUILD_TYPE=Release -DCNOR_BUILD_COMPILER=OFF -DCNOR_BUILD_CLI=OFF -DCNOR_BUILD_EXAMPLES=ON
cmake --build build-event-vm
./build-event-vm/examples/event-host/cnor_event_host build-event/examples/event-host/thermostat.tbc
```

The file reader and clock are desktop adapters. On firmware, pass the image
from flash to `cnor_vm_load`, wire the three natives to device I/O, and use
the device's event loop. Loading copies the image. `config.ctx` carries the
host state; the native table and context must outlive the VM.

## Lifecycle and checks

The host chooses 64 value slots, 8 call frames, a 256-byte string pool and
256 instructions per event. It resets the VM before each event, reclaiming
temporary strings and clearing script globals. Persistent relay state stays
in C. It checks all 100,000 events against the expected relay sequence,
checks exactly one output write per event, verifies no lh allocations occur
during processing, and verifies all VM allocations are released at shutdown.
It also exhausts a one-instruction budget and checks recovery on the next event.
Any failure exits nonzero. With tests enabled, the full build registers this
scenario in CTest; a VM-only build can run it manually with the same image.

The timing includes reset, native calls, script execution and result checks;
it excludes file I/O, loading and terminal output. It reports a batch mean,
not a worst-case latency. The first event is included; repeat runs to assess
noise. An instruction budget bounds VM instructions, not time spent inside a
native: production natives must also have bounded execution time.

## Memory accounting

`vm_heap_resident_bytes` counts live bytes requested through the lh allocator
after load; `load_peak_heap_bytes` also includes temporary verifier storage.
`vm_object_bytes` is separate. Tracking headers, allocator overhead, C stack,
stdio/OS memory and the input image buffer are excluded. The input buffer is
freed before event processing; it temporarily coexists with the VM image copy
at load. These figures are useful payload accounting, not total process RAM.
The tracker replaces the process's lh allocator and is intended for this
standalone executable; a larger application should retain its own allocator.

Measured on Windows x64, GCC 16.1.0, Release, 2026-10-27:

| Measurement | Value |
|---|---:|
| Image | 308 bytes |
| VM object | 464 bytes |
| Resident VM heap payload | 2,484 bytes |
| Load peak heap payload | 2,484 bytes |
| Allocations during 100,000 events | 0 |
| Mean VM instructions/event | 16 |
| Batch mean time/event, five runs | 136–243 ns |
| VM-only Windows executable, whole file with symbols | 456,114 bytes |
| VM-only executable sections, `text / data / bss` | 180,500 / 392 / 3,088 bytes |

These are desktop results, not STM32 measurements. Binary sizes depend on
toolchain, CRT linkage, symbols and build options; measure the executable
with `size` (sections) and the filesystem (whole file) on your target build.
The executable includes the desktop file reader, timing, reporting, allocator
tracker and C runtime; its size is not the size of the VM library alone.
